## 1. What Is This Project?

**Zk-AgriSure** is a **decentralized parametric crop insurance protocol** that uses **Zero-Knowledge Proofs (ZKPs)** to let farmers claim disaster insurance payouts **without revealing their exact GPS coordinates** to the blockchain.

### The Problem
Traditional crop insurance forces farmers to share their precise farm location with centralized insurers. This creates:
- **Privacy risks** — GPS data can be used for land surveillance, data breaches
- **Trust issues** — centralized middlemen control claim approvals
- **Fraud vulnerability** — farmers could claim fake locations after a disaster

### The Solution (3-Step Flow)

| Step | What Happens | Privacy |
|------|-------------|---------|
| **1. Policy Commitment** | Farmer drops a pin on a map. Browser computes a **Poseidon hash** of their GPS locally. Only the hash goes on-chain. | ✅ GPS never leaves the browser |
| **2. Oracle Trigger** | When a disaster occurs, a Chainlink Oracle broadcasts the disaster's bounding box (minLat, maxLat, minLon, maxLon) to the smart contract. | Public data |
| **3. Private Settlement** | Farmer's browser generates a **Groth16 ZK Proof** proving their farm is inside the disaster zone WITHOUT revealing coordinates. Smart contract verifies the proof on-chain and auto-releases the payout. | ✅ Proof, not coordinates |

### Key Technical Innovation
ZK circuits operate on **finite-field arithmetic** (integers only). GPS coordinates are floats (e.g., `12.9755`). The project solves this by:
1. **Scaling** all GPS values by `10^7` (10,000,000) → `12.9755` becomes `129755000`
2. **Offsetting** to eliminate negatives: Latitude `+= 90 × 10^7`, Longitude `+= 180 × 10^7`

## 4. Architecture Deep Dive

### 4.1 The ZK Circuit — [LocationVerifier.circom](file:///e:/SEM-7/Project/Distributed/project_workspace/zk-circuit/LocationVerifier.circom)

```
6 Signals:
  PUBLIC:  min_lat, max_lat, min_lon, max_lon  (Oracle's disaster bounding box)
  PRIVATE: farmer_lat, farmer_lon              (Farmer's hidden GPS)

4 Constraints (all 64-bit LessEqThan from circomlib):
  1. min_lat ≤ farmer_lat
  2. farmer_lat ≤ max_lat
  3. min_lon ≤ farmer_lon
  4. farmer_lon ≤ max_lon

If ALL 4 constraints pass → proof is valid → farmer is inside the disaster zone.
If ANY constraint fails → proof generation throws "Assert Failed" → claim rejected.
```

**Compilation pipeline (already done, artifacts exist):**
```bash
circom LocationVerifier.circom --r1cs --wasm --sym
snarkjs powersoftau new bn128 12 pot12_0000.ptau
snarkjs powersoftau contribute pot12_0000.ptau pot12_0001.ptau
snarkjs powersoftau prepare phase2 pot12_0001.ptau pot12_final.ptau
snarkjs groth16 setup LocationVerifier.r1cs pot12_final.ptau circuit_0000.zkey
snarkjs zkey contribute circuit_0000.zkey circuit_final.zkey
snarkjs zkey export verificationkey circuit_final.zkey verification_key.json
snarkjs zkey export solidityverifier circuit_final.zkey Groth16Verifier.sol
```

```
  ↓

  ↓

  ↓

  ↓

```

## 7. Coordinate Math Explained

### Why offsets?
- GPS latitude ranges from **-90 to +90** (negative = southern hemisphere)
- GPS longitude ranges from **-180 to +180** (negative = western hemisphere)
- Solidity `uint256` and Circom `LessEqThan` only work with **non-negative integers**

### The transformation pipeline:

```
Raw GPS: lat = -33.8688 (Sydney, Australia), lon = 151.2093

Step 1 — Scale by 10^7:
  lat_scaled = -33.8688 × 10,000,000 = -338,688,000
  lon_scaled = 151.2093 × 10,000,000 = 1,512,093,000

Step 2 — Add offset to eliminate negatives:
  lat_uint = -338,688,000 + 900,000,000 = 561,312,000   ← always positive ✓
  lon_uint = 1,512,093,000 + 1,800,000,000 = 3,312,093,000   ← always positive ✓

Reverse (on-chain → GPS float):
  lat = (561,312,000 - 900,000,000) / 10,000,000 = -33.8688 ✓
  lon = (3,312,093,000 - 1,800,000,000) / 10,000,000 = 151.2093 ✓
```

### Constants in code:
